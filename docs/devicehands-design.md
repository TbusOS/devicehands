# DeviceHands 框架设计

> 状态:v1.0(2026-11-16),项目所有者已确认,按它实施。改动本文要先经所有者同意。
> 范围:代码框架、仓库布局、协议、安装部署、实施阶段。不含各分析工具的具体设计。
> 现有架构说明见 [`architecture.md`](./architecture.md),本文是它的下一版目标。

## 1. 目标

DeviceHands 是给 AI 用的硬件调试工具:一个能适配不同板子的通用分析器。
本文要回答一个问题:**框架怎么搭,以后加设备、加连接方式、加分析工具、加厂商工具时不用大改。**

不在本文范围:

- 调试探针(J-Link、OpenOCD)的实现。只定接口,见 5.2。
- 团队功能(登录、权限、审计)的实现。只定接口,见 5.9。
- 各分析工具和模型协作功能的具体设计。

### 3.1 保留的设计

| 设计 | 为什么保留 |
|---|---|
| 传输抽象加单一工厂(`transport/base.py`、`factory.py`) | 13 个能力模块只认抽象类型,设备序列号只在一处校验 |

## 4. 核心概念

下面八个词是整个设计的词汇表,后文只用这些词。

| 词 | 是什么 | 没有它会怎样 |
|---|---|---|
| 台架(bench) | 插着板子的那台电脑上运行的服务。以前叫 agent,改名是为了不和「AI agent」混淆 | 访问硬件的代码会分散在两处,见 3.2 第 3 条 |
| 板子(board) | 一个被调试的设备,带一份描述:类型、有哪些口 | 只能用 adb 序列号指代设备,没有 adb 的板子无法表示 |
| 口(link) | 板子的一条物理连接:某个串口、某个 USB 功能 | 一板多口无法表达 |
| 设备能力(capability) | 对板子能做的一类事,例如执行命令、读日志、烧录 | 分析工具只能写死「我要 adb」,换一种连接就不能用 |
| 工具(tool) | 一个可以被 AI 或人调用的调试或分析功能 | 即现在的能力函数,但缺少统一登记 |
| 接入面(surface) | 工具对外的出口:命令行、MCP、网页接口 | — |
| 扩展(extension) | 仓库之外的包,往框架里加工具、口的驱动、烧录方法、板子描述 | 厂商只能改本仓库的代码 |
| 运行时(runtime) | 一个对象,持有配置、台架连接、登记表、事件总线 | 这些东西只能做成全局变量,见 3.2 第 5 条 |

## 5. 设计

### 5.1 总体结构

```
 接入面    命令行 · MCP · 网页接口(由工具登记表生成,不手写)
 ──────────────────────────────────────────────────────────────
 工具      日志 · 崩溃 · 性能 · 烧录 · 应用管理 · …  + 扩展加的
           (每个工具声明:需要哪些设备能力、适用哪些设备类型)
 ──────────────────────────────────────────────────────────────
 设备模型  板子 · 口 · 设备能力接口 · 板子描述 · 按板加锁
 ──────────────────────────────────────────────────────────────
 台架连接  本机台架 或 远程台架,同一套协议
 ══════════════════════ 协议(独立描述)═══════════════════════
 台架服务  口的驱动:串口 · adb · fastboot · 紧急下载 ·
           USB 网络 · 厂商工具;操作系统相关代码都在这一侧
```

依赖只能从上往下。横跨各层的公共部分(配置、工作区、事件、错误码、登记表)放在
基础层,基础层不导入上面任何一层。

这条规则用工具检查,不靠自觉:在自动构建里跑导入方向检查(`import-linter`),
违反就失败。现有的违反项(下层导入上层 5 条、同层接入面互相导入 5 条)登记在
`.importlinter` 的白名单里,逐条清掉;白名单里的条目修掉后不删,检查同样会失败。

### 5.2 设备能力和板子描述(对应 R1、R2、R4)

**决定**:分析工具不直接依赖某种连接方式,只依赖设备能力。每种口声明自己能提供
哪些能力,框架负责匹配。

| 设备能力 | 含义 | 第一阶段由谁提供 |
|---|---|---|
| `exec` | 执行一条命令,拿到输出和退出码 | adb、USB 网络上的 telnet 或 ssh、带 shell 的串口 |
| `console` | 双向字节流 | 串口、adb 交互终端 |
| `logs` | 读日志或持续接收日志 | adb、串口抓取、经 `exec` 读内核日志 |
| `files` | 和板子互传文件 | adb、USB 网络 |
| `flash` | 把镜像写进板子 | fastboot、紧急下载、厂商工具 |
| `reset` | 重启,或进入指定模式 | adb、fastboot、串口打断启动 |
| `forward` | 把板子上的端口映射出来 | adb、USB 网络 |
| `memory`、`registers`、`breakpoints` | 读写内存、读寄存器、debugger 断点 | 只定接口,留给调试探针 |

为什么这么分:

- 一块只接了串口的 MCU 板子提供 `console` 和 `logs`。需要 `exec` 的工具对它不出现,
  不会等到运行时才报错。
- 以后加调试探针,只是多一种提供 `memory` 等能力的口,工具这一层不用改。
- 重启模式这类安卓专有的概念从传输抽象里移出去,放进安卓类型的实现里。

没有选的做法:继续用一个大的传输基类,每种连接实现全部方法。原因是 MCU 和探针
没有 shell,基类里一半方法对它们没有意义,现在代码里 8 处按名字判断、7 处探测方法
是否存在,就是这个问题的表现。

板子描述是一份数据,不是代码,厂商可以自己写:

```toml
[board]
id   = "demo-board"
kind = "linux"              # android | linux | rtos | mcu

[[board.link]]
name = "console"
type = "serial"
baud = 115200

[[board.link]]
name = "usb"
type = "usb-net"            # 开机后经 USB 网卡连接
host = "192.0.2.10"
```

寻址写成 `台架/板子/口`,例如 `lab1/demo-board/console`。只有一台台架、一块板子时
可以省略前两段。

### 5.3 访问硬件只走台架一条路(对应 R5、R6)

**决定**:AI 助手这一侧不直接操作硬件。所有硬件访问都经过台架服务,用同一套协议。
单机时台架服务就在本机运行,由主程序自动启动,用户不需要配置。

```
 单机                              两台电脑
 ┌───────────────────────┐         ┌──────────┐      ┌──────────┐
 │ 主程序                │         │ 主程序   │      │ 台架服务 │
 │   │ 协议(本机管道)   │         │          │<─协议─│          │──> 板子
 │ 台架服务 ──> 板子     │         └──────────┘ 网络 └──────────┘
 └───────────────────────┘
```

没有它会怎样:同一个功能在单机和两台电脑两种用法下由两套代码实现,行为会不一样。
现在烧录就是这样,只有台架侧有。

为什么这么设计:

- 和操作系统相关的代码(串口枚举、USB 枚举、终端、进程管理)全部集中到台架服务,
  主程序可以写成与系统无关,三个系统的适配工作只做一次。
- 以后新加一种口的驱动,单机和两台电脑自动都能用。

没有选的做法:主程序保留一套本机直连的实现。它少启动一个进程,但每个功能要写
两遍、测两遍。

现有的端口隧道保留。串口和 adb 仍然可以映射成本机端口,别的软件(例如手机投屏
工具)照常能连。协议同时提供两种东西:原始字节通道,和带参数、带结果的操作。

迁移是逐步的:第一步先让现有的本机传输实现 5.2 的能力接口,工具照常工作;
台架服务具备对应能力后再把实现换过去,工具这一层没有改动。

### 5.4 工具登记一次,三个接入面自动生成(对应 R9、R10)

**决定**:每个工具写一个函数,带一份声明。命令行、MCP、网页接口由登记表生成。

```python
@tool(
    name="logs.dmesg",
    summary="Read the kernel log",
    requires=[Exec],
    kinds=["android", "linux"],
    risk="read",
)
async def dmesg(ctx: ToolContext, p: DmesgParams) -> Result[DmesgData]:
    ...
```

| 接入面 | 自动得到 |
|---|---|
| 命令行 | `dhands logs dmesg` |
| MCP | 工具 `dhands_logs_dmesg` |
| 网页接口 | `POST /api/tools/logs.dmesg`,以及由接口描述生成的前端类型 |

声明里的各项用途:

- `requires` 和 `kinds`:框架据此决定某块板子能不能用这个工具。
- `risk`(只读 / 改板子 / 动台架电脑):权限检查读这一项。默认规则沿用
  [`permissions.md`](./permissions.md) 里 2026-10-23 的决定:板子上的操作不拦截、不先问;
  只有会动到台架电脑本身的操作受限。团队版可以通过 5.9 的接口换成更严的规则。
- 参数和结果的类型:生成命令行参数、MCP 的输入描述、接口文档。

持续输出的工具(例如跟着看日志)用同一种声明,结果类型是事件流,三个接入面各有
对应的呈现方式。

现有的 93 个命令、36 个 MCP 工具、96 个接口分组迁移。迁移期间手写的包装和生成的
包装并存,迁完一组删一组。

### 5.5 协议独立描述,带版本协商(对应 R12)

**决定**:主程序和台架服务之间的协议写成一份与语言无关的描述,放在仓库的
`protocol/` 目录,包含四样东西:

1. 每种帧的结构描述(JSON Schema)。
2. 一批样例帧文件。Python 和 Rust 的测试都读这同一批文件。
3. 顺序和超时规则的文字说明。例如先登记通道再发开通道请求,这类规则写不进结构描述。
4. 一套一致性测试:把台架服务当成独立程序启动,只通过协议交互。任何实现都必须
   通过它才能发布。

握手时协商版本,两边版本范围没有交集就拒绝连接,并给出明确的错误码:

```
 台架 → 主程序   hello     { proto: {min: 1, max: 2}, impl, build, os,
                             ops: [...], boards: [...] }
 主程序 → 台架   hello_ok  { proto: 2 }
```

没有它会怎样:现在协议改了,新旧混用时不报错,表现是某个功能偶尔失灵。

对未知内容的处理统一成一条规则:未知字段忽略;未知帧类型回一个错误帧,不断开连接。
现在两边的做法正好相反(主程序断开,台架侧不出声地忽略)。

操作表里参数的校验规则现在是 Python 写法的正则表达式,会随握手发到对端。
改成各语言通用的写法,并在样例帧里覆盖。

### 5.6 Rust 的位置(对应 R12、R6)

**决定**:Rust 用来写台架服务。主程序保持 Python。

为什么是台架服务:

- 按 5.3,和操作系统打交道的代码都在台架服务里。Rust 编出来是单个可执行文件,
  三个系统各编一份,用户不用装 Python。
- 主程序的工作是等外部:等串口、等 USB、等模型返回。换语言不会变快,而 MCP 的官方
  开发包和模型相关的库以 Python 最全。

板上 agent 用同一个程序:把台架服务交叉编译到安卓或 Linux 板子上运行,它把板子
自己当作唯一的一块板子,通过同一套协议提供 `exec`、`logs`、`files`。这样板上和台架
是一套协议、一份代码。RTOS 和 MCU 上放不下程序,由台架侧经串口或探针访问。
板上是否运行模型是另一件事,不在本文范围。

没有选的做法:

- 整体用 Rust 重写。43,850 行 Python 换不来性能,代价是重做。
- 把 Rust 做成 Python 的扩展模块。安装包要按系统和芯片分别编译,而目前没有量出
  需要它的计算热点。
- 板上 agent 做成安卓应用(旧设计)。它只能用在安卓上,不满足 R1。

过渡方式:现有的 Python 台架程序保留,作为功能完整的参考实现。Rust 版按操作逐个
补齐,每补一个都要通过 5.5 的一致性测试。主程序根据握手时上报的操作表判断对端
支持什么,所以两个实现可以同时存在。Rust 版功能补齐后,Python 版停止维护。

### 5.7 扩展机制(对应 R8、R3)

扩展分两侧,做法不同。

**主程序一侧:Python 扩展包。** 扩展包通过 Python 的入口点机制登记自己,安装后
自动被发现。它可以添加工具、板子描述、模型后端、网页视图。扩展只允许导入
`devicehands.sdk` 这一个包,这个包的接口按版本号规则保持兼容。

**台架一侧:声明式的工具清单,不注入代码。** 厂商的烧录工具或分析工具用一份清单
登记:可执行文件在哪、允许哪些参数、参数怎么校验、输出怎么解析、它提供哪种设备
能力。台架服务按清单调用。

```toml
[[tool]]
name     = "vendor-flash"
provides = "flash"
exe      = "C:/tools/vendor_dl.exe"
args     = ["--port", "{port}", "--image", "{image}"]
timeout  = 600
```

为什么台架侧不让扩展执行任意代码:

- 台架服务将来是 Rust 程序,加载不了 Python 代码。
- 台架电脑直接连着硬件,只执行登记过的操作是现有的安全边界,要保持。

现有的厂商工具透传已经是这个思路,这里是把它定成正式的扩展格式。USB 上的厂商
下载工具(R3)走的就是这条路。

### 5.8 运行时对象代替全局变量(对应 R7、R13)

**决定**:配置、台架连接、登记表、事件总线都挂在一个运行时对象上,由入口创建,
往下传递。代码里不再有模块级的全局状态。

没有它会怎样:一个进程只能连一台台架;测试之间互相影响(现在 14 类全局对象里,
测试只会自动重置 4 类);新旧两套程序在同一台电脑上会抢同一对端口。

事件总线只保留一个。现有两个里有一个没有任何订阅方。

### 5.9 团队功能的接口和许可证(对应 R14)

- 每个请求带一个「调用者」对象。默认实现是「本机单用户,全部允许」。
- 权限检查、审计记录各有一个接口,默认实现分别是「全部允许」和「写本地日志」。
- 团队版是一个扩展包,替换这三个默认实现。核心代码不需要为它改动。
- 许可证:仓库内全部是 Apache-2.0。进内核的代码(内核模块、eBPF 程序)如果以后
  要加,单独放一个目录,用 GPL-2.0。外部贡献者提交代码前签贡献者协议。

### 5.10 操作系统相关代码(对应 R6)

- 主程序不出现只在某个系统上存在的模块。自动构建在三个系统上各跑一遍导入检查和
  单元测试。
- 网页终端现在用的伪终端只有 Linux 和 macOS 有。按 5.3,它改成经台架服务的字节
  通道,主程序这一侧不再需要伪终端。
- 配置和数据目录按各系统的惯例放置,用 `platformdirs` 取路径。
- 文件名里不出现 Windows 不允许的字符。现在工作区目录名允许冒号
  (`infra/workspace.py:29,126`)。

### 5.11 命名、配置、目录、端口(对应 R13)

新旧两套要能装在同一台电脑上同时运行,下面每一项都必须不同。

## 7. 安装部署(对应 R5、R6)

两个安装包,覆盖三种情况。

| 情况 | 装什么 | 步骤 |
|---|---|---|
| 单机 | 主程序包 | ① 一条命令安装 ② `dhands doctor` 检查环境,缺什么给出安装办法 ③ 在 AI 助手里登记 MCP |
| A 电脑 | 主程序包(和单机是同一个) | 同上,再加:④ `dhands hub start`,得到一个配对码 |
| B 电脑 | 台架包 | ① 下载一个可执行文件 ② 运行,填 A 的地址和配对码 |

- 主程序包是纯 Python,用 `pip` 或 `uv` 安装,三个系统步骤相同。
- 台架服务每个系统一个可执行文件。它同时作为主程序包的依赖发布,所以单机安装时
  自动带上,用户感觉不到它的存在。
- B 电脑的台架包可以从 A 的网页上下载,保证两边版本一致。
- 配对码一次有效,换来的凭证只存在两台电脑各自的配置里。
- 更新:主程序把新版台架程序推过去,新版连不回来就自动退回旧版。这是现有机制,保留。

## 8. USB 范围怎么落到设计上(对应 R3)

| 用法 | 口的类型 | 提供的设备能力 |
|---|---|---|
| adb | `adb` | exec · logs · files · reset · forward |
| fastboot | `fastboot` | flash · reset |
| 紧急下载 | `edl` | flash |
| USB 网卡加 telnet 或 ssh | `usb-net` | exec · files · forward |
| USB 虚拟串口 | `serial` | console · logs |
| 厂商下载工具 | 按 5.7 的清单登记 | flash |

「开机后经 USB 和板子传数据」对应 `files` 和 `forward` 两种能力。安卓板子由 adb 提供,
Linux 板子由 USB 网卡提供。工具只声明需要 `files`,不关心下面用的是哪一种。

## 9. 实施阶段

每个阶段结束时全部测试通过,旧功能照常可用。没有「先拆掉再重建」的阶段。

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 基线 | 本仓库建测试环境并记下基线;三个系统的自动构建;导入方向检查(现有违反项登记白名单);文档清理(设计决策记录合成一份、过时内容更正) | 三个系统上导入检查和单元测试都通过 |
| P1 改名 | 按 5.11 改名;资源文件打进安装包;主程序在 Windows 上能导入和启动 | 新旧两套在同一台电脑上同时运行;在三个系统上用正常方式安装后能打开网页 |
| P2 骨架 | 运行时对象;工具登记表和三个接入面的生成;设备能力接口和板子描述,先支持安卓和 Linux 两种设备类型;迁移两组工具做试点(一组简单的,一组持续输出的) | 试点工具在三个接入面行为一致;代码里不再按传输名字做判断 |
| P3 安卓和 Linux 调试 | 一板多口(多个串口加 USB);Linux 板子经 USB 网卡的 telnet 连接和文件传输;现有安卓调试功能全部迁到登记表,补上 MCP 里缺的烧录和台架类工具;Linux 的通用分析工具逐个加入;Python 版台架程序补上 macOS 和 Ubuntu 的启动方式 | 一块安卓板和一块 Linux 板,在命令行、MCP、网页三处都能完成:连接、执行命令、读日志、传文件、烧录 |
| P4 协议 | `protocol/` 目录;版本协商;修掉 5 处不一致;一致性测试覆盖握手、三种通道、全部操作 | Python 版台架程序通过全部一致性测试 |
| P5 Rust 台架 | `crates/`;先做握手、串口、adb 隧道;三个系统出可执行文件;单机时自动启动本机台架;再按操作逐个补齐 | Rust 版通过它已声明支持的全部一致性测试;单机下能烧录 |
| P6 扩展 | 入口点机制;台架侧工具清单格式;一个示例扩展;开发包文档 | 示例扩展不改本仓库任何文件就能加一个工具和一种烧录方法 |

分两条线同时推进,两条线改的文件不重叠:

```
 主线      P0 ──> P1 ──> P2 ──> P3 ──────────> P6
 Rust 线   P0 ──> P4 ──> P5(先做握手 · 串口 · adb 隧道)
                          └─ 「单机自动启动本机台架」等 P2 完成后再做
```

- 主线的依据是 R15:P0 到 P2 是把安卓和 Linux 调试做好所必需的地基,做完立刻进 P3。
  P3 里新加的功能直接按新骨架写,不会在旧结构上写一遍再迁移。
- Rust 线的依据是 R12:P0 之后就开始 P4,不等主线。P4 只新增 `protocol/` 目录和测试,
  P5 只新增 `crates/` 目录,和主线互不影响。

P6 之后依次是:RTOS 和 MCU 的串口调试、模型协作、板上运行台架服务、团队版。
P3 之前,RTOS 和 MCU 只在设备类型和能力接口里留位置,不写实现。

## 10. 风险和没定的事

| 项 | 说明 |
|---|---|
| 迁移量大 | 93 个命令、96 个接口要逐组迁到登记表。靠新旧并存和分组迁移控制,每组迁完即可发布 |
| Rust 版补齐需要时间 | 期间两个台架实现并存。协议的每次改动先改 `protocol/`,两个实现由一致性测试保证一致 |
| 台架服务随主程序包发布 | 需要为每个系统和芯片架构各出一个安装包,依赖自动构建。P0 要先把自动构建做起来 |
| 本机没有 Rust 工具链 | 开发机上找不到 `cargo`、`rustc`、`rustup`;交叉编译到 Windows 和安卓还没试过 |
| 没定:板上运行什么模型 | 记录里有四种说法,需要单独讨论 |
| 没定:网页应用重新设计的范围 | 和现有界面的关系没有记录 |
