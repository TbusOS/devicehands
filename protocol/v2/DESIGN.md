# 协议 v2 设计

> 状态:2026-11-16 定稿。2026-11-17 按本文做出了 schema、样例帧、`patterns.json`、
> `framing.md`、`sequences.md`(第 5 节第 1 步);实现见第 5 节。
> 依据:`docs/devicehands-design.md` 第 5.5 节;v1 现状见 [`../v1/`](../v1/),
> 文中的 G1…G21 是 [`../v1/known-gaps.md`](../v1/known-gaps.md) 的条目编号。

## 1. v2 是什么

主程序和台架服务之间的协议的第二版。它做三件事:

1. 握手时协商版本,对不上就明确拒绝。
2. 把 v1 里两边做法不一样、或者只写在代码里的规则定成一份。
3. 去掉 v1 为兼容更早的台架程序而留下的分支。

没有它会怎样:第二个实现(Rust)只能照着 Python 代码的行为去猜,而 v1 的行为里有
21 处问题,其中 5 处是两边已经对不上。

## 2. 和 v1 的关系:不兼容,新主程序只讲 v2 及以后

DeviceHands 的主程序不接受 v1 的台架程序。

为什么可以这么做:改名后新旧两套各自独立安装,端口、凭证、HTTP 头都不同
(设计文档 5.11)。旧的 `alb` 主程序继续配旧的台架程序,新主程序遇不到旧台架。
本仓库里的 Python 台架程序和主程序在同一次改动里一起升到 v2。

没有选的做法:新主程序同时支持 v1。v1 为「新主程序配旧台架」已经有 11 条分支
(缺 `ops` 时从 `caps` 推一张旧表等),继续带着它们,Rust 实现就要把这些也实现一遍。

## 3. 决定

### 3.1 版本协商(G1)

```
 台架 → 主程序   hello     { verb, proto: {min: 2, max: 2}, bench_id, … }
 主程序 → 台架   hello_ok  { verb, proto: 2 }
```

- 主程序取两边范围交集里最大的版本;没有交集就回 `error`(码
  `PROTO_VERSION_UNSUPPORTED`,带上自己的 `supported: {min, max}`),然后用关闭码
  1002 关掉连接。
- 台架收到这个错误后不再重连,在状态页和日志里写明是哪一边需要升级。
- 台架等 `hello_ok` 最多 10 秒(v1 没有这个超时)。
- 每一帧里的 `v` 字段取消。版本是会话的属性,握手时定下来。

版本号的规则:只加可选字段、只加新的操作或新的错误码,不升版本;删字段、改含义、
改必填项,升版本。主程序同时支持当前版本和上一个版本。

### 3.2 名字和凭证

| 项 | v1 | v2 |
|---|---|---|
| 信令路径 | `/agent/connect` | `/bench/connect` |
| 数据路径 | `/agent/channel?cid=…` | `/bench/channel?cid=…` |
| 帧里的标识 | `agent_id` | `bench_id` |
| HTTP 头 | `x-alb-token`、`x-alb-csecret` | `x-dhands-token`、`x-dhands-csecret` |
| 信令的凭证 | 放在 `hello` 帧体里 | 放在 HTTP 头 `x-dhands-token` 里,和数据连接一致 |

- 凭证不再出现在任何帧里,帧可以整条写进日志。
- 数据连接上「头不存在就读查询参数」的退路取消。

### 3.3 未知内容和坏帧(G7、G8、G20)

两边用同一套规则:

| 收到 | 处理 |
|---|---|
| 帧里有不认识的字段 | 忽略这个字段 |
| 不认识的 `verb` | 回 `error`(码 `UNKNOWN_VERB`),会话继续 |
| 不是 JSON、是 JSON 但不是对象、缺必填字段、类型不对 | 回 `error`(码 `BAD_FRAME`),会话继续 |
| 信令上的二进制消息 | 回 `error`(码 `BAD_FRAME`),会话继续 |

```
 error { verb: "error", code, message, re? }
```

`re` 是出错那一帧的 `id`(见 3.4),取不到就不带。任何输入都不能让进程退出。

必填字段按 schema 严格检查,不再靠「字段不在就当作旧版本」来推断(G12)。
缺省值写在 schema 里,两边用同一个。

### 3.4 请求和回复对上号

主程序发的 `list_adb`、`list_com`、`restart_adb` 带 `id`;台架的回复带 `re`,
值等于请求的 `id`。v1 没有编号,回复顺序不保证,主程序只能「收到就覆盖缓存」。

`open_channel` 继续用 `cid` 对应,不另加 `id`。

### 3.5 通道(G13、G16、G18)

- `channel_error` 加错误码:`{ verb, cid, code, reason }`。
- 台架拨回失败时也要发 `channel_error`(信令连接还在,发得出去)。v1 只写日志,
  主程序只能等超时。
- `open_channel` 缺 `cid`:按 3.3 回 `BAD_FRAME`。v1 是不出声地忽略。
- `channel_error` 只接受来自拥有这个 `cid` 的那条信令连接。v1 里任何已通过鉴权的
  连接都能让任意 `cid` 失败。
- 去掉 `close_channel`、`channel_opened`、`channel_closed` 三种帧:两边都不发。
  拨回成功就是打开成功,关闭数据连接就是关闭通道。
- 去掉 `open_channel` 里的 `role`:台架不读它。重试规则由通道类型决定,写在
  `sequences.md` 里:tcp 不重试,serial 最多 3 次,job 不重试。

### 3.6 操作和参数(G6、G9、G4、G5)

- **操作名是开放集合。** 台架在 `hello` 的操作表里报什么,主程序就能调什么。
  主程序不再有写死的操作枚举。这是厂商工具能登记进来的前提(设计文档 5.7)。
- **事件种类是固定集合**:`accepted`、`progress`、`file`、`done`。
- **进度阶段 `phase` 是开放的字符串**,由操作自己定。接收方遇到不认识的阶段,
  按普通进度显示。
- **`done` 失败时必须带非空的错误码。** 请求本身不合格用 `BENCH_PARAM_REJECTED`。
- **参数规则**:
  - `pattern` 永远是整串匹配,两端的锚点不用写。
  - 只允许一个各语言都能执行的正则子集:字符类、量词、分组、`|`;
    `\d`、`\w`、`\s` 只指 ASCII;不允许 `\A`、`\Z`、前后查找、反向引用。
  - 分区名的规则作为烧录操作的参数规则,随操作表下发。v1 里它只在两边代码里
    各存一份。
  - `protocol/v2/patterns.json` 放一批(规则,输入,应该通过还是拒绝)的样例,
    两个实现都要通过。
- **整数参数只接受 JSON 整数。** v1 里主程序会把十进制字符串转成整数,台架不接受。
- **请求里多出的键,台架拒绝**(`BENCH_PARAM_REJECTED`)。v1 里主程序拒绝、台架忽略。

### 3.7 hello 的内容(G2)

```
 hello {
   verb, proto: {min, max},
   bench_id, name,
   impl:  { lang: "python" | "rust", build },
   os:    "windows" | "macos" | "linux",
   ops:   [ 操作表 ],
   boards: [ … ],
   update: { … }          可选:上一次自更新的结果
 }
```

- `caps` 取消:能力由操作表推出。
- `flash_partitions` 取消:并入烧录操作的参数规则(3.6)。
- `agent_version` 取消:由 `proto` 代替。
- `boards` 暂时沿用 v1 的形状。设计文档 5.2 的板子描述(类型、口)做出来时,
  作为新增字段加进来,按 3.1 的规则不升版本。

### 3.8 大小和时间

写进 `sequences.md`,两边用同一组值:

| 项 | 值 |
|---|---|
| 等 `hello` / 等 `hello_ok` | 10 秒 |
| 心跳间隔 / 多久没收到帧就断开 | 20 秒 / 60 秒 |
| 单个 job 帧的上限 | 8 MiB,发送方也要检查(G14) |
| `done` 里 `error` 文本的上限 | 4 KiB,超出截断(G14) |

## 4. 不在 v2 里的

| 项 | 说明 |
|---|---|
| 信令断开时正在跑的作业怎么办(G19) | v2 保持现状:作业被取消。让作业在断线后继续并能重新接上,需要作业编号和结果留存,单独设计 |
| `done` 的 `data` 每个操作的形状 | v2 仍是任意对象。操作表里给每个操作附结果的结构描述,留到工具登记表(设计文档 5.4)做出来时一起做 |
| 本机台架用什么连接 | 单机时主程序和本机台架之间跑同一套帧,走本机回环还是管道,P5 定 |
| 板上运行台架服务 | 用同一套协议,板子把自己当作唯一的一块板子。P6 之后 |

## 5. 实施顺序

v2 的实现要改主程序和台架程序的代码,排在 P1 改名之后,避免和改名互相冲突。

1. `protocol/v2/schema/`、`frames/`、`patterns.json`、`framing.md`、`sequences.md`:
   从 v1 的文件出发按第 3 节改。
2. 一致性测试:把台架程序当成独立进程启动,只通过协议交互。测试自己起一个最小的
   主程序替身。台架程序的启动命令是参数,Python 版和 Rust 版用同一套测试。
   覆盖:握手成功、版本对不上、未知 verb、坏帧、心跳、三种通道各开一次、
   一个不碰硬件的操作(用假的 fastboot 可执行文件)。
   为此台架程序要能通过配置指定 adb 端口和 fastboot 路径,心跳间隔能在测试里调短。
3. 主程序改成 v2。
4. Python 台架程序改成 v2,通过一致性测试。
5. Rust 台架从握手、心跳、串口通道、tcp 通道开始,每加一项都要通过对应的一致性测试。
